# Front-End · Components

You build exactly what `docs/design-specs.md` and the mockups show, with code the next agent can read. `HARD-RULES.md` (next to this file) is the one-page digest — re-read it after compaction.

## 1. Where things go (the `src/` layout from `docs/architecture.md`)

| What | Where | Rule |
|---|---|---|
| Routes & pages | `src/app/(app)/…`, `src/app/embed/…` | a page composes components; little logic of its own |
| Primitives | `src/components/ui/` | shadcn/ui, added with the shadcn CLI — don't hand-copy, don't fork without reason |
| Feature components | `src/components/<feature>/` | one component per file, named like the design spec's component map |
| App hooks | `src/hooks/` | UI behaviour only (media query, disclosure) — API hooks are generated, never here |
| API layer | `src/lib/api/generated/` | **generated by Orval — never edit**; you own only `src/lib/api/fetcher.ts` |

Touch only the files your step owns. Anything outside → a finding in your report.

## 2. Server vs client components

- **Server Components by default.** Add `"use client"` only to the smallest component that needs state, effects or browser APIs — never on a page or layout.
- Data that's the same for everyone on first load can be fetched on the server; anything the user changes or that must refresh uses the generated TanStack Query hooks in a client component.
- Props crossing the server → client boundary must be serialisable (no functions, no class instances).
- Server-only code (`src/lib/server/`) is never imported from client components — it's the backend lane's anyway.

## 3. TypeScript discipline

- `strict` on. No `any` (use `unknown` and narrow), no `as` to silence an error, no `!` without a comment, no `@ts-ignore`.
- Props as `interface`, extending the native element's attributes when wrapping one (`interface ButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement>`); `children: React.ReactNode`.
- Types for API data come from `src/lib/api/generated/model` — never redeclare them.

## 4. Design fidelity

- **Tokens only:** Tailwind utilities that map to the theme generated from DESIGN.md (`src/app/theme.css`). No raw hex, no arbitrary values (`text-[#00D4A0]`, `p-[13px]`), no fonts outside DESIGN.md. Missing token → contract question to the designer, never a one-off value.
- Build from the screen's mockup (`design/mockups/SCR-NN-*.html`) and its screenshots; match hierarchy, spacing rhythm and copy exactly.
- Every state in the screen's state matrix is implemented — empty, loading (skeleton in the real layout shape), error with retry, success, disabled. A screen with only the happy path isn't done.
- Variants from the component map (button-primary, badge-error…) map to component props (`variant="primary"`), not ad-hoc class strings at call sites.

## 5. Composition

- Small components with one job; compose, don't configure (prefer `children`/slots over 10 boolean props).
- No business rules in components — if a rule matters (who can cancel, how totals are computed), it lives on the server and the UI reflects the API's answer.
- Copy comes from the design spec's Copy table; user-facing strings live in one place per feature.
