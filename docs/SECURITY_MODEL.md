# Security Model: Northside quote requests

**Status:** proposed (locked at Gate 2), revised after the S0 threat model (`.baseleap/reviews/S0.md`; S0 ids cited inline) and for PRD v1.2 (ledger rulings of 2026-11-20: 1B consent resolves SEC-6, 3A staff passwords, 4A sign-in limits resolves SEC-11, the SEC-14 event cap) · **Reviewed against by:** bl-security (S0 threat model, Phase 4 review) · **Decisions:** 0002, 0003, 0004

## System and scope
Covers the Next.js app on Vercel (pages, `/api/*` route handlers, `src/proxy.ts`), the Supabase project in ca-central-1 (Postgres with RLS, Auth, the private `quote-photos` Storage bucket), the Vercel Cron calls to `/api/jobs/*`, and the outbound calls to the GoHighLevel API for the test sub-account. Out of scope: GoHighLevel's own security and hosting location (OQ-12), Supabase and Vercel platform security, the homeowner's device. There are no embedded screens (NG-11), no payments (NG-5), no email or SMS (NG-1) and no AI features (NG-13).

## Authentication and sessions
- **Staff accounts:** exactly two, created by Baseleap through the Supabase dashboard or admin API, plus a row each in `public.staff`. No public sign-up, no reset email, no magic links, no OAuth (NG-4).
- **Passwords (ruling 3A, FR-27).** Baseleap sets each password, at least 12 characters and different for the two accounts, hands it to its owner by phone, and resets a forgotten one from the Supabase dashboard (Authentication → Users). **The app has no screen, link, route or database function to change or reset a password, and sends no email** (AC-004.10): `docs/openapi.yaml` has no such operation and `supabase/tests/rls/all_tables.sql` asserts no `password`, `reset` or `recover` function exists in `public`. The Supabase Auth recovery and OTP endpoints exist but deliver nothing, because no custom SMTP sender is configured (invariant 21). Dashboard settings for devops (runbook): Authentication → Providers → Email → minimum password length 12, and "Require reauthentication when changing password" on (Supabase password security guide, https://supabase.com/docs/guides/auth/password-security, read 2026-11-20). Whether the dashboard's own "create user" applies the minimum length is unverified, so the 12-character rule is Baseleap's procedure either way. The direct Auth password-change call that remains is under "Out of scope / accepted risk".
- **Sign-in** goes through `POST /api/auth/sign-in` (`src/lib/server/auth/sign-in.ts`), which enforces two limits (FR-9, ruling 4A; resolves S0 SEC-11): **per email**, 5 failures within 15 minutes pause that email for 5 minutes; **per network address**, 20 failures within 15 minutes, across any emails, pause that address for 15 minutes. Each count restarts when its pause ends (only failures at or after the end of the key's latest pause count). A paused sign-in is refused with 429 `sign_in_paused` even with the right password, with one body for both limits and for real and unknown emails, and **no `Retry-After` header** (5 vs 15 minutes would say which limit applied). An email with no account is hashed and counted like any other. A successful sign-in is not counted. Wrong password and unknown email give the same 401 body. On success the `@supabase/ssr` cookies are set (`Secure`, `SameSite=Lax`; not `httpOnly`, because the browser client reads the access token for the bearer header).
- **The limits are one database call, made before Supabase Auth is called** (S0 SEC-3): `take_sign_in_attempt(email_hash, ip_hash)` takes an advisory lock on the email and then on the address (always in that order), checks both pauses through `app_private.sign_in_pause_until()` (which records a pause in `sign_in_pauses` when a limit is reached), and either refuses or records the attempt as a failure up front and returns its id. Only when the user ends up signed in **and** is staff does the route call `mark_sign_in_succeeded(attempt_id)`. Parallel guesses therefore count against each other, and a crash mid-way counts as a failure. The route never counts and inserts separately. The counters live in Postgres, so every Vercel instance sees the same counts. The email HMAC input is `email|v1|<lower-cased, trimmed email>`; the address key is as in "Network address".
- **Fail closed (AC-004.13).** If `take_sign_in_attempt()` errors for any reason (database unreachable, missing key, timeout), the route answers 503 `sign_in_unavailable` ("Sign-in is unavailable. Try again in a few minutes."), never calls Supabase Auth and starts no session. This is the opposite of the public form, which accepts a submission when its counter fails (FR-8, AC-003.5), because a blocked homeowner loses a job while a blocked owner can wait.
- **Return to the tab opened (FR-26, AC-004.14).** `src/proxy.ts` sends a signed-out page visit to `/sign-in?next=<path>`; after sign-in the page goes to `next` only if it passes invariant 22, otherwise to `/requests`.
- **API authentication:** the frontend fetcher sends `Authorization: Bearer` with the Supabase access token. Route handlers never authenticate from cookies, so `/api` has no CSRF surface. `src/proxy.ts` reads the cookies only to refresh the session and redirect signed-out page visits to `/sign-in`.
- **7-day sessions:** Supabase Free cannot time-box sessions, so `app_private.is_staff()` requires the JWT's `session_id` to name an `auth.sessions` row created less than 7 days ago. Every staff policy and RPC uses it; the route helper calls `current_staff()` and returns 401 `session_expired` when it is empty, and the frontend signs out and opens SCR-03.

## The public `formToken` scheme
The public operations (`createQuoteRequest`, `submitQuoteRequest`) do not use `security: []`. They declare `formToken`, an `X-Form-Token` header:
- Issued by `src/lib/server/form-token.ts` when the Request a quote page renders on the server: `v1.{issued_at_ms}.{nonce_uuid}.{signature}`, where the signature is base64url HMAC-SHA256 over `form-token|v1|issued_at|nonce` with `APP_SIGNING_SECRET`.
- Verified with a constant-time compare. Valid from 3 seconds (the FR-8 time trap) to 24 hours after issue. Too young gives the generic 400 `submission_refused`; expired gives 400 `form_expired` and the page fetches a fresh token with `router.refresh()` without losing what was typed; a bad signature gives 401 `form_token_invalid`.
- The nonce becomes `quote_requests.submission_key` (unique). Replaying a token returns the same request, so one token can never create more than one request. The submit call must present the token that created the request.
- It proves "this came from a page we rendered at least 3 seconds ago", not who the person is. It is not a secret from the homeowner and carries no personal data.

**One token per page load (S0 SEC-2).** The scheme is only correct if no two visitors, and no two submissions, ever share a nonce:
- **Per-request rendering, never cached (frontend requirement).** `src/app/(public)/page.tsx` calls `await connection()` from `next/server` before `issueFormToken()`, and the response carries `Cache-Control: private, no-store` (set explicitly for `/` in `next.config.*` `headers()` by the A2 scaffold; nothing may opt `/` back into static rendering or caching). A token never appears in a static, ISR or CDN-cached response. (Next.js prerenders a page that uses no request-time API; `connection()` stops prerendering at that point: https://nextjs.org/docs/app/api-reference/functions/connection, updated 2026-11-06.) The nonce-based CSP in invariant 13 needs dynamic rendering on every page anyway.
- **A fresh token after every completed submission (frontend requirement).** When `submitQuoteRequest` succeeds, or `createQuoteRequest` answers 200 with `submission_state: submitted`, the page drops its token and calls `router.refresh()` for a new one before another submission is allowed. The nonce of a completed submission is kept in `sessionStorage`; on mount and on `pageshow` (Back button, bfcache) a page whose token is in that list refreshes first.
- **A used token never takes different details (database).** `start_quote_request()` compares the fields: same token and same fields is a replay (200, the same request); same token, different fields, request still pending: the pending request is updated and its uploaded photos are cleared (200); same token, different fields, already submitted: refused with 409 `form_already_used`, nothing changes, and the page refreshes its token and keeps what was typed. Homeowner B's details are never merged into homeowner A's request.
- **Two concurrent creates with one token resolve to one request (database).** `start_quote_request()` takes a transaction-level advisory lock on the nonce before it reads, so the second call waits and then sees the first one's row (a replay). The unique `submission_key` index is the backstop: if a `23505` on it ever reaches the route, the route answers it as the replay (200), never 500. Tested in `supabase/tests/functions/submission_and_limits.sql`.

`uploadQuotePhoto` declares `supabasePublishableKey` (the public `apikey` header). That key grants nothing beyond what RLS allows the anon role, which is the single insert policy on `storage.objects`.

## Security invariants (each must hold; each is checkable)
1. RLS is **enabled and forced** with at least one policy on every table in `public`, in the migration that creates it. anon has no privilege on any `public` table, and authenticated has `select` only (granted explicitly, never inherited from project defaults). Checked per table in `supabase/tests/rls/<table>.sql` and across all tables, including future ones, in `supabase/tests/rls/all_tables.sql`. Forcing RLS keeps the table owner's own code (views, owner-owned functions) under the policies; it relies on `postgres` and `service_role` having `BYPASSRLS`, which Supabase documents ("On Supabase the owner is `postgres`, which has `bypassrls`"; "the `service_role` Postgres role, which has the `bypassrls` attribute": https://supabase.com/docs/guides/database/postgres/row-level-security, read 2026-11-19) and `all_tables.sql` asserts. See "Database functions" below.
2. `SUPABASE_SERVICE_ROLE_KEY` is read only in `src/lib/server/admin.ts`. Only these modules import it: `src/lib/server/services/submissions.ts` (create, photo check, complete), `src/lib/server/auth/sign-in.ts` (`sign_in_attempts`, `staff_signed_in`), `src/lib/server/events.ts` (refusal and photo-failure events), `src/lib/server/integrations/ghl/runner.ts` (claim and settle jobs, read the request's contact fields), `src/lib/server/jobs/housekeeping.ts` (purges). It never appears in client bundles, `NEXT_PUBLIC_*` variables, logs or fixtures.
3. Every route under `src/app/api/` except `/api/health`, `/api/auth/sign-in`, the two `formToken` routes and `/api/jobs/*` rejects a request without a bearer token for which `public.current_staff()` returns a row.
4. Staff never write a table directly: `authenticated` has `select` only, and every staff change goes through a `security definer` RPC that checks `app_private.is_staff()` and the caller's `version`.
5. A request is invisible to staff until it is `submitted`, and a reference number exists only for a submitted request (`quote_requests_submitted_has_reference`, issued only in `complete_quote_request`).
6. Photos are never public: the bucket is private, no policy grants anon or non-staff `select`, staff can read only objects recorded in `quote_photos` (which exist only for submitted requests), there is no update or delete policy, and signed URLs live 900 seconds and are created per staff request with the staff member's own token.
7. A photo is stored only if its first bytes are a JPEG (`FF D8 FF`), PNG (`89 50 4E 47 0D 0A 1A 0A`) or WebP (`RIFF....WEBP`) signature and it is at most 5,242,880 bytes; a PNG or WebP whose header declares more than 12,000 pixels on either side (read from the IHDR or VP8/VP8L/VP8X header in the same first bytes) is refused too (decompression bomb). Anything refused is deleted before the request is completed. Staff screens show photos with a plain `<img>` on the signed URL, never through `next/image` remote optimisation (frontend requirement).
8. Spam refusals store nothing in `quote_requests`, issue no reference, and the honeypot and time-trap refusals return byte-identical bodies (FR-8, AC-003.2).
9. `GHL_PRIVATE_INTEGRATION_TOKEN` is read only in `src/lib/server/integrations/ghl/client.ts`. It is never logged, never stored in the database (not in Vault either: the PRD keeps it in the environment only), never sent to the browser, and failure records hold an error class only. When `VERCEL_ENV` is `production`, the client sends the token only to `https://services.leadconnectorhq.com` and ignores `GHL_API_BASE_URL` (S0 SEC-20); the override exists for tests and previews.
10. The app calls only these GoHighLevel endpoints: `GET /contacts/search/duplicate`, `POST /contacts`, `POST /contacts/{id}/tags`, `DELETE /contacts/{id}/tags`, and removes only the four stage tags it owns (`docs/integration-contract.md`). A contact id from GHL is used only if it matches `^[A-Za-z0-9_-]{1,100}$` and is put into a path with `encodeURIComponent`.
11. No personal data in `events.properties`, `ghl_sync_jobs` or logs: ids, enums, booleans and counts only (`events.properties` keys are limited by a check constraint to the metrics-spec names, now including `marketing_consent` and `count`). Network addresses and sign-in emails are stored only as HMAC-SHA256 with `APP_SIGNING_SECRET` (inputs `ip|v1|...` and `email|v1|...`, so each hash has its own domain), in `rate_limit_hits`, `spam_refusal_windows`, `sign_in_attempts` and `sign_in_pauses` only, and purged after 24 hours. **Database, Storage and provider errors count as logging** (S0 SEC-5): Postgres check and unique violations carry the whole failing row in `details`. They are logged as `{ error_class, code }` only, never their `message`, `details`, `hint`, body or the error object itself. `src/lib/server/log.ts` writes only the fields listed in `docs/architecture.md` "Observability" and drops any other field. Every route handler is wrapped by `src/lib/server/http.ts`, which catches unhandled errors and logs them the same way (so Next.js never prints a raw error). Problem responses never include database or provider text: `23514` and `23505` map to the contract's field errors or to the replay, built from our own messages.
12. `/api/jobs/*` returns 401 unless `CRON_SECRET` is set, at least 32 characters long, and `Authorization` equals `Bearer <CRON_SECRET>` under a constant-time compare of equal-length buffers (different lengths fail without comparing). An unset or short secret never matches anything, so `Bearer undefined`, `Bearer ` and no header all give 401 (S0 SEC-4).
13. Every page sends `Content-Security-Policy` with a fresh nonce per request, set in `src/proxy.ts` as in the Next.js guide (https://nextjs.org/docs/app/guides/content-security-policy, updated 2026-03-20): `default-src 'self'; script-src 'self' 'nonce-<per request>' 'strict-dynamic'; style-src 'self' 'unsafe-inline'; img-src 'self' blob: data: <NEXT_PUBLIC_SUPABASE_URL>; connect-src 'self' <NEXT_PUBLIC_SUPABASE_URL>; font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests` (development adds `'unsafe-eval'` only). Session cookies are readable by JavaScript by design, so this CSP is what keeps an XSS from becoming a 7-day takeover (S0 SEC-15). Plus `X-Frame-Options: DENY` (no embedding, NG-11), `Referrer-Policy: strict-origin-when-cross-origin` and `X-Content-Type-Options: nosniff`. `style-src` keeps `'unsafe-inline'` because the UI library sets inline style attributes; scripts never get it.
14. Homeowner text is rendered as text only; nothing renders stored text as HTML.
15. `src/lib/server/env.ts` is the only reader of `APP_SIGNING_SECRET` and `CRON_SECRET` and refuses either when unset or shorter than 32 characters. Form-token issue and verify and the HMAC helpers then throw, so `GET /` fails, the two `formToken` routes and `POST /api/auth/sign-in` answer 503 `service_unavailable`, and `/api/jobs/*` answer 401. Nothing falls back to a default or empty key (S0 SEC-4). `scripts/env-check.mjs` (devops) fails when either name is missing from the Production or Preview rows.
16. The rate limit, the spam event cap and the sign-in limits are each one database call that locks, counts and records (`take_submission_slot` through `start_quote_request`, `record_spam_refusal`, and `take_sign_in_attempt` for both the per-email and the per-address limit); no route counts and inserts in two calls, and no counter lives in server memory (S0 SEC-3, ruling 4A).
17. A GHL job is settled only by the runner holding its current lease: `claim_ghl_job` leases one job with a new `lease_id`, and `finish_ghl_job` ignores a result whose lease id is missing or not the current one (S0 SEC-7).
18. **Nothing reaches GoHighLevel without consent (ruling 1B, SEC-6).** `marketing_consent` is true only when the request body's `marketing_consent` is the JSON value `true`; anything else is stored as false (the route coerces, the database defaults). A trigger on `ghl_sync_jobs` (`before insert or update of request_id, kind`) refuses any job for a request without consent, whether inserted or produced by repointing or re-kinding an existing job (S0 SEC-23), a column check refuses a `ghl_contact_id` on such a request, and a trigger refuses any change to a stored request's consent or consent time (NG-16). So an unticked request is never searched, created, linked or tagged in GHL, and `request_ghl_copy_retry` refuses it. Tested in `supabase/tests/functions/complete_and_sync.sql`, `status_and_quote.sql` and `supabase/tests/rls/ghl_sync_jobs.sql`.
19. Sign-in fails closed: any error from `take_sign_in_attempt` gives 503 `sign_in_unavailable` without calling Supabase Auth. A 429 `sign_in_paused` has the same body for both limits and every email and carries no `Retry-After` (AC-004.5, AC-004.11, AC-004.12, AC-004.13).
20. `spam_submission_blocked` is written only by `record_spam_refusal`: at most one event per address and reason per 10-minute window (later refusals raise its `count`) and at most 1,000 per Hamilton day; past the daily cap nothing is written at all, not even a window row, so a flood cannot grow the database (FR-8, S0 SEC-14). The refusal response is identical in every case, and if the call fails the refusal still happens (logging fails open). The address key lives only in `spam_refusal_windows`, never in `events`.
21. There is no password change or reset path in the app (ruling 3A, FR-27, AC-004.10): no page, no link, no `/api` route, no database function, no email. Custom SMTP is never configured on these Supabase projects without a security review, so Supabase's own recovery and OTP endpoints deliver nothing (S0 SEC-10).
22. The post-sign-in redirect (`next`) is followed only when it matches `^/(requests|pipeline)(/[0-9a-f-]{36})?$`; anything else, including absolute URLs, `//host`, encoded slashes and query strings, lands on `/requests` (FR-26; no open redirect).

## Network address (rate limit, spam event cap, sign-in limit)
The address is `x-real-ip` as set by Vercel (fallback: the first `x-forwarded-for` entry; `request.ip` is not available in route handlers). An IPv4 address is used whole. An IPv6 address is cut to its /64 prefix (the first four hextets, after expanding `::` and lower-casing) before hashing, because one client controls a whole /64 (S0 SEC-3). The HMAC-SHA256 input is `ip|v1|<address or /64 prefix>` with `APP_SIGNING_SECRET`; only the hash is stored. The address is never written to `events` or logs. The /64 cut and the hash input are unit-tested in the backend lane. Three uses, one hash:
- **Submission rate limit** (`rate_limit_hits`, time of each accepted submission). `start_quote_request()` calls `take_submission_slot()` under a per-address advisory lock, so parallel creates cannot all pass; replays of a token take no slot. If the counter cannot be used, or no address is known, the submission is accepted (FR-8, AC-003.5).
- **Spam event cap** (`spam_refusal_windows`, one row per address, reason and 10-minute window). With no address known, the route passes the hash of `ip|v1|unknown`, so address-less refusals share one window per reason.
- **Sign-in limit** (`sign_in_attempts.ip_hash`, `sign_in_pauses`). With no address known, the route passes the hash of `ip|v1|unknown`, so address-less sign-ins share one counter (fails closed: they are limited together, never unlimited). On Vercel `x-real-ip` is always present, so this only matters in local runs.

**Retention:** every row holding an address hash is deleted 24 hours after it was written by the housekeeping job (`rate_limit_hits`, `spam_refusal_windows`, `sign_in_attempts`, `sign_in_pauses`). The longest window any limit needs is 15 minutes plus a 15-minute pause, so 24 hours is ample and no hash outlives a day (metrics spec, Privacy).

| `app_private.is_staff`, `public.current_staff` | definer (postgres) | authenticated, service_role | is the check | `postgres` BYPASSRLS and read access to `auth.sessions` |
| `app_private.photo_upload_allowed` | definer (postgres) | anon, authenticated (schema not exposed over REST) | is the check | `postgres` BYPASSRLS |
| `list_quote_requests`, `weekly_counts`, `app_private.weekly_counts_at` | invoker (caller) | authenticated | RLS | nothing extra |
Every function sets `search_path = ''` and qualifies every name. If `postgres` ever lacked BYPASSRLS, the definer functions would fail closed: the staff policies would apply to `postgres` (a member of `authenticated`), so staff reads and writes would error or return nothing, and uploads would be refused. Nothing would be exposed. A2 runs `supabase/tests/rls/all_tables.sql` on staging; if its BYPASSRLS assertions fail, A2 stops and raises a contract question instead of dropping `force`.

## Finding classes (what counts as a problem here)
- **Critical:** a request, photo or personal field readable without a fresh staff session; any client write that skips the RPCs (audit, version or stage-tag job bypassed); service-role key or GHL token exposed; a way to create requests without the spam checks; a photo reachable by a URL that is not a short-lived signed URL; any GHL call or job for a request without offers consent; any in-app way to change or reset a password.
- **Important:** a refusal that reveals which spam check failed; a sign-in response that reveals which limit applied or whether an email has an account; sign-in that proceeds when the counters cannot be read; personal data in events, job rows or logs; a 7-day-old session still reading data; missing constant-time comparison on the form token or cron secret; a GHL write outside the four allowed endpoints, removal of a tag the app does not own, or any change to an existing contact's fields; an open redirect through `next`; framing allowed.
- **Minor:** missing non-critical headers; verbose error text that leaks no data.

## Out of scope / accepted risk
- **Direct calls to the Supabase Auth API** skip our per-email and per-address limits (the Password Verification hook is a Teams-plan feature). Accepted for $0: passwords are at least 12 characters and set by Baseleap, Supabase applies its own per-IP auth limits, and sign-up is off.
- **Lockout trade-off (ruling 4A, S0 SEC-11, accepted by Matthew).** Anyone who knows the owner's email can keep her out in 5-minute stretches, and people sharing a network address with a guesser (an office, a phone carrier) are paused together for 15 minutes; she waits or phones Baseleap. Guessing is capped at 1,440 attempts a day per email and 1,920 a day per address (PRD FR-9).
- **A signed-in staff member can change her own password by calling Supabase Auth directly** (`PUT /auth/v1/user` with her own session), outside the app. It needs her valid session and only affects her own account; with "Require reauthentication when changing password" on, a session older than 24 hours would need an emailed nonce, which is never delivered (no custom SMTP). The app offers no way to do it (invariant 21), so FR-27 holds for the app; Baseleap's dashboard reset remains the recovery path.
- **A tick is the homeowner's word (ruling 1B).** Nothing verifies that the email or phone belongs to the person who ticked the box, so a stranger's address can become a GHL contact. Acceptable on the test sub-account; OQ-16 before any real client.
- **Abandoned uploads.** Someone passing the spam checks can upload up to 15 MB per pending request that is never submitted; at most 5 per address (IPv6: per /64) per 10 minutes, enforced atomically, purged daily. A distributed attack could still fill the 1 GB Free storage until the next purge. Accepted for the rehearsal; for a real client see the storage DECISION line in the A1 report.
- **Supabase Auth recovery and OTP endpoints exist** (S0 SEC-10). "No reset email, no magic links" holds only because no custom SMTP sender is configured: Supabase's default sender delivers only to members of the Supabase organisation. If custom SMTP were added, `recover` and `otp` would sign a staff member in with a fresh session. Rule: custom SMTP is never configured on these projects without a security review (runbook line, devops).
- **Search text in request URLs** (S0 SEC-13). `GET /api/quote-requests?q=` puts what the owner typed (part of a name or phone) in the URL, which Vercel's platform request logs record (outside our logs and our control, short retention). Accepted because search is a Could story used only by the two staff, and our own logs never write the query string (Observability). Moving `q` into a body would break the list's GET semantics for one Could story. Matthew can reverse this at Gate 2.
- **Photo EXIF data** (S0 SEC-16). Photos keep their EXIF metadata, which may include the location. Accepted: only the two staff can open them, through short-lived signed URLs, and the location is the address the homeowner typed anyway.
- **A leaked request id** within its 60-minute window lets someone add photos to that pending request, only up to the planned count and only of the allowed types; the submit step re-checks every file.
- **GoHighLevel's data location** is unverified (OQ-12); acceptable only because the sub-account is a test account.

## Known limitations & compensating controls
- The rate limit keys on one address (IPv6: one /64); behind shared mobile networks several real people may share one (PRD risk). Refusals are recorded as `spam_submission_blocked` with a `count` (capped, invariant 20) so the threshold can be tuned; on a day that hits the 1,000-event ceiling the blocked share reads low (accepted in FR-8).
- If a future Supabase release removes the `postgres` role's read access to `auth.sessions`, `is_staff()` returns false for everyone (fails closed); A2's RLS tests on staging prove it works today.
- The design depends on `postgres` and `service_role` keeping `BYPASSRLS` (see "Database functions"). Losing it fails closed; `supabase/tests/rls/all_tables.sql` catches it on every test run.
