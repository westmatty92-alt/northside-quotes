### REV-1 in detail

The round 1 scenario was: runner A reads "quoted", is slow, runner B reads "won" and finishes, A's calls land last and leave `quote-quoted`. With the fix, A's last call is always followed by A's own read. A can only report success when that read equals the stage it applied. If A's calls landed after B's, B's status change was committed before A's read, so A sees "won" and applies it itself after its stale calls. The last call to land therefore always belongs to a pass whose stage was still current when it was verified. I also walked the interleaving where A's remove lands between B's add and B's remove (the contact briefly has no stage tag): B reports success, but A's check then fails and A repairs it; the test named "second call slow" exercises exactly that. Both the stage-tag job and `link()` use it, and shared-contact requests converge because `ghl_stage_for_request` answers per contact. The cost is one extra read per attempt and no extra provider call when nothing moved (asserted). The bound of three passes keeps an attempt inside the 120 s lease (at most six tag calls of 10 s, plus the search on the link path).

The architect's optional CQ (a status change on another request of the same contact, made in the one database round trip between a link's last call and its settle) is not needed to close REV-1. I agree it is optional: the contact then carries a stage that a real owner action chose, and the next status change repairs it. It is recorded below as a residual, not a finding.

### REV-2 in detail

- **Server.** An unchanged resend is still `replayed` and keeps its uploads (the AC-002.6 flow); any change of count, type or size at any position is `updated` for a pending request and `token_used` (409) for a submitted one. A failed cleanup repeats by itself: while an object older than the current plan survives, every resend is `updated` again. `start_quote_request` keeps one signature (no PostgREST overload), `security invoker`, granted to `service_role` only, and the advisory lock and unique key from SEC-2 are untouched. ## Requested checks (answers to the six items)

1. **Test honesty (`tests/api/**`, `tests/integrations/**`).** Isolated well: every counter is keyed by hashes signed with a per-file random secret and random addresses, so rate-limit, sign-in and spam windows cannot collide between runs; seeds carry a random per-file tag (`inboxTools`); the far-future-week technique makes the week arithmetic exact; every file deletes what it made and then asserts nothing is left; the GHL tests use an offline simulator and unique phones and emails, so the global contact-match rule cannot cross-link runs; no `skip`, `only` or `fixme` in either folder. Not isolated in round 1: the housekeeping purge and the CI concurrency (REV-3) and the current-week count comparison with its 30-second wait (REV-4); **both closed at `04dd79a`** (see the re-review section). Also brittle: `unpaired-surrogates.test.ts:77-96` pins PostgREST's `PGRST102` answer with a live call (REV-12). The pgTAP file `submission_and_limits.sql` runs on staging in a rolled-back transaction and takes the global `spam_refusal_day` advisory lock, so a concurrent API test can wait on it; it needs fewer than 997 real spam events that day. I rate that low.
2. **Bearer token on staff calls.** All ten call sites pass `useStaffRequest()`: `queries.ts:32,38,44,50,71` (the list fetcher spreads it), `use-pipeline.ts:66`, `requests-list.tsx:44`, `status-control.tsx:38`, `quote-form.tsx:51`, `ghl-card.tsx:94`. The token is read when the call is made (`staff-session.tsx` `createAuthRequest`), so a refreshed token is picked up. No raw `fetch` or Supabase data call exists in `src/components`, `src/app` pages or `src/hooks`. Only `useSignIn` (public) omits it, correctly. The rule is by convention only: REV-11. (The fixes touched no staff call site.)
3. **Idempotency and races.** Board and list moves: the version is checked under a row lock (`functions.sql:523-530`), a stale one is 409 `stale_version`, five parallel writers give one winner (`quote.test.ts:242`), and the UI allows one press per card. Replay with the same token: serialised per token by an advisory lock plus the unique key (`functions.sql:108`); in round 1 the plan was not compared (REV-2), **now it is, and a left-over upload forces a re-clear (closed)**. `complete_quote_request` locks the row and returns the same reference on a replay. GHL leases: one job per claim with `skip locked`, settle only with the claim's lease (`functions.sql:632-643`, `:692-694`); in round 1 correct for the database but not for the provider side effect (REV-1), **now the attempt re-reads and converges (closed)**. `after()` is registered only after the database commit and its failure is logged without changing the answer; no `maxDuration` on those two routes (REV-8); a retry after a lost response schedules nothing (REV-13).
4. **N+1 and unbounded queries.** None on the server. The list is one RPC, clamped to 101 rows by the database and 100 by the schema, keyset-paged on the partial inbox indexes (`list-plan.test.ts` asserts index use, no sort, under 250 ms at 2,400 rows); search is a filtered scan by design (about 2,400 rows a year).
