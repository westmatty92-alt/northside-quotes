## Requested checks (answers to the six items)

1. **Test honesty (`tests/api/**`, `tests/integrations/**`).** Isolated well: every counter is keyed by hashes signed with a per-file random secret and random addresses, so rate-limit, sign-in and spam windows cannot collide between runs; seeds carry a random per-file tag (`inboxTools`); the far-future-week technique makes the week arithmetic exact; every file deletes what it made and then asserts nothing is left; the GHL tests use an offline simulator and unique phones and emails, so the global contact-match rule cannot cross-link runs; no `skip`, `only` or `fixme` in either folder. Not isolated: the housekeeping purge and the CI concurrency (REV-3, the likely cause of BE1's one-off failure), and the current-week count comparison with its 30-second wait (REV-4). Also brittle: `unpaired-surrogates.test.ts:77-96` pins PostgREST's `PGRST102` answer with a live call (REV-12). The pgTAP file `submission_and_limits.sql` runs on staging in a rolled-back transaction and takes the global `spam_refusal_day` advisory lock, so a concurrent API test can wait on it; it needs fewer than 997 real spam events that day. I rate that low.
2. **Bearer token on staff calls.** All ten call sites pass `useStaffRequest()`: `queries.ts:32,38,44,50,71` (the list fetcher spreads it), `use-pipeline.ts:66`, `requests-list.tsx:44`, `status-control.tsx:38`, `quote-form.tsx:51`, `ghl-card.tsx:94`. The token is read when the call is made (`staff-session.tsx` `createAuthRequest`), so a refreshed token is picked up. No raw `fetch` or Supabase data call exists in `src/components`, `src/app` pages or `src/hooks`. Only `useSignIn` (public) omits it, correctly. The rule is by convention only: REV-11.
3. **Idempotency and races.** Board and list moves: the version is checked under a row lock (`functions.sql:523-530`), a stale one is 409 `stale_version`, five parallel writers give one winner (`quote.test.ts:242`), and the UI allows one press per card. Replay with the same token: serialised per token by an advisory lock plus the unique key (`functions.sql:108`), but the plan is not compared (REV-2). `complete_quote_request` locks the row and returns the same reference on a replay. GHL leases: one job per claim with `skip locked`, settle only with the claim's lease (`functions.sql:632-643`, `:692-694`); correct for the database, not for the provider side effect (REV-1). `after()` is registered only after the database commit and its failure is logged without changing the answer; no `maxDuration` on those two routes (REV-8); a retry after a lost response schedules nothing (REV-13).
4. **N+1 and unbounded queries.** None on the server. The list is one RPC, clamped to 101 rows by the database and 100 by the schema, keyset-paged on the partial inbox indexes (`list-plan.test.ts` asserts index use, no sort, under 250 ms at 2,400 rows); search is a filtered scan by design (about 2,400 rows a year). The board is four parallel list calls of 50 with a per-column "Show more". The weekly count is one RPC with three indexed counts. The detail is four parallel reads plus one Storage call. Housekeeping and the GHL runner loop with caps (1,000 requests a run; 240 s of a 300 s budget). Two client-side costs, both Minor (REV-7).
5. **known-paths drift.** The list is guarded by `tests/unit/proxy/known-paths.test.ts`, which runs in CI's `verify`, so a new page or route under `src/app` fails the build rather than answering 404 in production. It is maintainable for 20 routes, with one blind spot and a hand-kept list (REV-6).
6. **Duplication.** Yes, in three places: the backend validation helpers (the NUL/surrogate check, the field-error builder and the UUID pattern each exist in more than one service, and the code-point length rule exists in only one of them), the staff-side `next` allow-list and the phone rule across lanes. See Cross-lane consolidation.
