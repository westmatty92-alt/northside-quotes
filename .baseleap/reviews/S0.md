### SEC-1 · Critical · Confirmed — RLS is enabled but not forced on any of the 8 tables
| | |
|---|---|
| **Where** | `supabase/migrations/20261120000200_staff.sql:60` (`staff`) · `20261120000300_quote_requests.sql:88` (`quote_requests`), `:115` (`quote_photos`), `:141` (`quote_request_status_changes`) · `20261120000400_ghl_sync.sql:47` (`ghl_sync_jobs`) · `20261120000500_events_and_limits.sql:30` (`events`), `:50` (`rate_limit_hits`), `:70` (`sign_in_attempts`) |
| **Breaks** | sec-access §3 house rule (every new table: `enable` **and** `force row level security`; missing `force` is Critical, drill of Nov 18 2026) · SECURITY_MODEL invariant 1 |
| **What's wrong** | Each table has `enable row level security` and no `force row level security`. None of the 8 tables has the `force` line. The RLS tests check only `relrowsecurity` (e.g. `supabase/tests/rls/staff.sql:21`), so nothing would catch it. The write-policy half of the rule holds: no table has a client write policy, and the only client-written row (a Storage object) is tied to its parent pending request in `photo_upload_allowed` (`20261120000700_storage.sql:40-46`). |
| **Scenario** | Without `force`, the table owner skips every policy. Today there is no such view, so this is a house-rule breach with no exploit path found yet. That is also why it must be fixed before code starts piling on top. |
| **Fix direction** | Force RLS on all 8 tables, assert it in the tests, and prove on staging that the owner roles still bypass RLS so the definer RPCs keep working. |
| **Patch directive** | **Owner: bl-architect** (migrations, tests, SECURITY_MODEL). (3) SECURITY_MODEL invariant 1: "RLS is enabled **and forced**". (4) A2 on staging: `select rolname, rolbypassrls from pg_roles where rolname in ('postgres','service_role');` must return `true` for both. In that case stop and raise a contract question instead of dropping `force`. The function tests in `supabase/tests/functions/*.sql` must still pass. |

### SEC-2 · Critical · Likely — The form-token page is not required to render per request, so a cached page shares one nonce across homeowners
| | |
|---|---|
| **Where** | `docs/SECURITY_MODEL.md:49` ("Issued … when the Request a quote page renders on the server") · `docs/architecture.md:53` (Public pages: "renders the token from `issueFormToken()`") · `docs/openapi.yaml:107-111` (same token again → 200 with the same request; changed fields update the pending request and clear its photos; a submitted one returns its reference) |
| **Breaks** | FR-3 / AC-001.6 and AC-001.7 (one request per submission, two requests allowed per homeowner) · SECURITY_MODEL "The public formToken scheme" (the nonce identifies one page load) |
| **What's wrong** | The nonce is the request's `submission_key`, so the scheme is only correct if every page load gets its own token. Next.js App Router prerenders a page statically at build time when it uses no dynamic API. `crypto.randomUUID()` and `Date.now()` alone do not opt out, and Vercel then serves the HTML from its CDN. Nothing in the blueprint requires dynamic rendering or `no-store`. The same flaw appears in one browser: after a successful submit, the Back button or bfcache shows the same token again. |
| **Scenario** | Homeowner B loads the cached page carrying homeowner A's token. B's create counts as a replay of A's request: A's pending fields are overwritten and A's photos cleared. If A has already submitted, B gets 200 with A's reference and B's request is never stored. B also sees a confirmation that isn't theirs. After 24 h the baked-in token expires and `router.refresh()` returns the same static page, so the form is dead until the next deploy. |
| **Fix direction** | Make per-request rendering and no caching a stated invariant, require a fresh token after every completed submission, and treat a concurrent duplicate create as a replay. |
| **Patch directive** | **Owner: bl-architect** (SECURITY_MODEL "The public formToken scheme", architecture "Modules → Public pages"). Implementers: frontend (page), backend (create), QA (tests). Add to SECURITY_MODEL after line 51: "The Request a quote page is rendered per request and never cached: `src/app/(public)/page.tsx` calls `await connection()` from `next/server` before `issueFormToken()`, and the response carries `Cache-Control: private, no-store`. A token never appears in a static, ISR or CDN-cached response. After a submission completes (or a create replay returns `submitted`), the page drops its token and gets a fresh one before another submission is allowed. Two concurrent creates with the same nonce: the loser's unique violation (`23505` on `submission_key`) is answered as the replay (200), never 500." Add the same line to architecture "Public pages". Add to the S0-driven QA list: two GETs of `/` return different nonces and a `Cache-Control` containing `no-store`; submitting, pressing Back and submitting different details creates two requests with two references. |
| **Owner hint** | architect (contract), frontend, backend |
| **Signature** | `public-form: form token page cacheable, nonce shared across visitors` |

### SEC-3 · Important · Likely — The submission rate limit can be beaten with parallel requests and IPv6 rotation; the same race affects the sign-in pause
| | |
|---|---|
| **Where** | `docs/SECURITY_MODEL.md:72-73` (address from the first `x-forwarded-for` entry, HMAC, row per accepted submission) · `supabase/migrations/20261120000500_events_and_limits.sql:41-58` (`rate_limit_hits`, no atomic helper) · variant: `:60-76` (`sign_in_attempts`) and SECURITY_MODEL:43 |
| **Breaks** | FR-8 / AC-003.4 (5 accepted per 10 minutes per address) · SECURITY_MODEL "Out of scope / accepted risk" (storage exhaustion was accepted only for distributed attackers) |
| **What's wrong** | (a) The design reads the count, then inserts a row, in application code through PostgREST: two calls with no lock. N parallel creates all read the count before any insert commits, and all pass. (b) The key is the full address. An IPv6 client controls at least a /64 (2^64 addresses), so every request can come from a new address. (c) The sign-in pause has the same count-then-record race (lower impact, because direct Auth API calls already skip it). |
| **Scenario** | One VPS fetches 100 pages, waits 3 s and fires 100 creates at once, or rotates its IPv6 address. All 100 are accepted, and each can hold 15 MB of uploads, so 1 GB of Free Storage fills in about 70 requests. Real homeowners' photo uploads then fail until the next daily purge, and it can be repeated every day. |
| **Fix direction** | One database call that locks per key, counts and records; key IPv6 by its /64 prefix; take the address from Vercel's `x-real-ip`. |
| **Patch directive** | **Owner: bl-architect** (new function in `20261120000600_functions.sql`, SECURITY_MODEL "Network address for the rate limit"). Add `public.take_submission_slot(p_ip_hash text, p_limit integer default 5, p_window interval default interval '10 minutes') returns boolean`, `language plpgsql security definer set search_path = ''`, body: `perform pg_advisory_xact_lock(hashtextextended('submission:' \|\| p_ip_hash, 0));` then `if (select count(*) from public.rate_limit_hits where ip_hash = p_ip_hash and created_at > now() - p_window) >= p_limit then return false; end if; insert into public.rate_limit_hits (ip_hash) values (p_ip_hash); return true;`. `revoke all … from public, anon, authenticated; grant execute … to service_role;`. Add the matching `public.record_sign_in_failure_and_check(p_email_hash text) returns integer` (same lock pattern, returns failures in the window) for the pause. Rewrite SECURITY_MODEL:73: "The address is `x-real-ip` as set by Vercel (fallback: the first `x-forwarded-for` entry). An IPv4 address is used whole; an IPv6 address is cut to its /64 prefix (first four hextets, normalised) before the HMAC. The check and the record are one call to `take_submission_slot`; the route never counts and inserts separately. If the call fails, the submission is accepted (AC-003.5)." Add a function test: 20 calls with one hash in one transaction accept exactly 5. QA: 20 parallel creates from one address accept exactly 5. |
| **Owner hint** | architect, backend |
| **Signature** | `rate-limit: count-then-insert race and full-IPv6 key` |

### SEC-4 · Important · Needs verification — Cron and signing secrets are not required to fail closed when unset or short
| | |
|---|---|
| **Where** | `docs/SECURITY_MODEL.md:68` (invariant 12: constant-time compare only) · `:49` (form token signed with `APP_SIGNING_SECRET`) · `docs/architecture.md:223-224` (both marked new) · `docs/ops/account-setup.md:95-96, 110` (rows on Production and every Preview branch, added by hand) |
| **Breaks** | SECURITY_MODEL invariant 12 and the formToken scheme · sec-appsec "Crypto & tokens" |
| **What's wrong** | The usual route check compares `authorization` with `` `Bearer ${process.env.CRON_SECRET}` ``. If the variable is missing on a deployment (a lane preview, a new environment, a typo), the expected value becomes `Bearer undefined`, and a timing-safe compare of equal strings passes. An empty `APP_SIGNING_SECRET` makes HMAC keys empty: anyone can mint tokens with any `issued_at` (skipping the time trap), and the IP and email hashes stop being keyed. Nothing in the blueprint says to fail closed. |
| **Scenario** | A preview deployed without `CRON_SECRET` lets anyone send `Authorization: Bearer undefined` to `/api/jobs/housekeeping` and `/api/jobs/ghl-sync`. Without `APP_SIGNING_SECRET`, a bot signs its own tokens dated 10 seconds ago. |
| **Fix direction** | State the fail-closed rule and minimum lengths in the security model, enforce them in one env module, and check that the names exist. |
| **Patch directive** | **Owner: bl-architect** (SECURITY_MODEL). Implementers: backend (`src/lib/server/env.ts`), devops (`scripts/env-check.mjs`). Rewrite invariant 12: "`/api/jobs/*` returns 401 unless `CRON_SECRET` is set, at least 32 characters, and `Authorization` equals `Bearer <CRON_SECRET>` under a constant-time compare of equal-length buffers. An unset or short secret never matches anything." Add invariant 15: "`src/lib/server/env.ts` reads `APP_SIGNING_SECRET` and `CRON_SECRET` and refuses values under 32 characters. Token issue and verify and the HMAC helpers throw, so the route answers 503 `service_unavailable` instead of falling back to a default." Devops: `env-check.mjs` fails when either name is missing from the Production or Preview rows. QA probe: `Bearer undefined`, `Bearer ` and no header each give 401 on both job routes. |
| **Owner hint** | architect, backend, devops |
| **Signature** | `secrets: cron/signing secret not fail-closed when unset` |

### SEC-5 · Important · Likely — Database error objects carry the homeowner's whole row and are not excluded from logs or responses
| | |
|---|---|
| **Where** | `docs/SECURITY_MODEL.md:67` (invariant 11 lists events, job rows and logs, but not error objects) · `docs/architecture.md:49` (`23514 → 422` mapping) · `:260` (log fields) |
| **Breaks** | SECURITY_MODEL invariant 11 and finding class "Important: personal data in … logs" · sec-secrets §3 |

### SEC-7 · Important · Needs verification — A GHL job lease can expire mid-batch, and `finish_ghl_job` accepts a result from a runner that no longer holds it
| | |
|---|---|
| **Where** | `supabase/migrations/20261120000600_functions.sql:253-277` (`claim_ghl_jobs`: one 120 s lease for up to 50 jobs) · `:305-311` (`finish_ghl_job` settles any pending or waiting job, with no lease check) · `docs/architecture.md:243` (runner batches of 25) · `docs/decisions/0004-ghl-sync-and-retry-schedule.md:17` (the lease is meant to stop the same job running twice) |
| **Breaks** | FR-15 / AC-009.4 ("never creates a second contact for the same request") · decision 0004 item 6 |
| **What's wrong** | One contact copy can take three GHL calls with a 10 s timeout each. Another runner (an `after()` drain from a new submission, or the next cron) then claims and runs them too. Both search, find nothing and create. GHL's "Allow Duplicate Contact: off" is the only backstop, and it is still unconfirmed (integration-contract open questions). |
| **Scenario** | After a GHL slowdown leaves 25 copies waiting, the cron run and a homeowner's `after()` drain both process the same copies, and the test sub-account ends up with two contacts for one request. |
| **Fix direction** | Lease one job at a time (or size the lease to the batch), and make a late settle harmless with a lease id. |
| **Patch directive** | **Owner: bl-architect** (`20261120000400_ghl_sync.sql`, `20261120000600_functions.sql`, `docs/integration-contract.md` "Sync jobs"). (1) Add `lease_id uuid` to `ghl_sync_jobs`. (2) `claim_ghl_jobs` sets `lease_id = gen_random_uuid()` with `locked_until`. (3) Change the signature to `finish_ghl_job(p_job_id uuid, p_lease_id uuid, p_outcome text, p_error_class text default null, p_contact_id text default null)`: after the `for update` read, `if v_job.lease_id is distinct from p_lease_id then return v_job; end if;`, and clear `lease_id` on every settle. (4) Integration contract: "The runner claims one job at a time (`p_limit = 1`) with a 120 s lease, which covers the worst case of three 10 s calls, and stops claiming when less than 60 s of the 300 s function budget is left." Add a function test: claim, expire the lease, claim again, then finish with the first lease id leaves the row unchanged. |

Owner: architect.
- **SEC-9** · `supabase/migrations/20261120000500_events_and_limits.sql:20`: `properties` accepts any keys, so a future server bug could store personal data. Fix: add `check (properties - array['request_id','urgency','photo_count','minutes_since_submit','from_status','to_status','user_id','attempt_number','error_class','reason','photo_index'] = '{}'::jsonb)`. Owner: architect.
- **SEC-10** · `docs/SECURITY_MODEL.md:42, 89-93`: "no reset email, no magic links" holds only because no mail sender is configured (the default sender delivers to Supabase org members only). The Auth `recover` and `otp` endpoints still exist and would sign a staff member in with a fresh session if custom SMTP is ever added. Fix: add this to "Out of scope / accepted risk", with a runbook line that custom SMTP must not be configured without a security review. Owner: architect, devops.
- **SEC-11** · `docs/PRD.md:100` (FR-9), `docs/SECURITY_MODEL.md:43`: anyone who knows the owner's email can keep her signed out by failing 5 times every 15 minutes, because the pause applies "even with the right password". Separately, our route calls Supabase Auth from Vercel's egress addresses, so Supabase's per-IP auth limit may throttle all our users together (to verify on staging). Fix: Matthew acknowledges the lockout trade-off at Gate 2 (PM owns FR-9). The architect adds a per-address failure limit on `/api/auth/sign-in` (reusing `take_submission_slot` with a `signin:` prefix) so bulk guessing is stopped before it reaches Supabase. Owner: pm, architect.
- **SEC-12** · `supabase/migrations/20261120000300_quote_requests.sql:55`: `ghl_contact_id` is only length-checked, but it is later placed in `/contacts/{id}/tags` URLs. Fix: `check (ghl_contact_id ~ '^[A-Za-z0-9_-]{1,100}$')`, and the integration contract requires the runner to validate the id and `encodeURIComponent` it before use. Owner: architect, integration.
- **SEC-13** · `docs/openapi.yaml:57-63`: search text (names, phone digits) travels in the query string, which Vercel records in its request logs. A hand-built keyset or search filter (`.or(...)` with interpolated `q` or cursor values) would also allow PostgREST filter injection, bounded by RLS to what staff can already read. Fix: run search and keyset paging through a security-invoker RPC with typed parameters (no filter strings built from input), and record the request-log exposure as accepted for a Could story or move `q` into a POST body. Owner: architect, backend.
- **SEC-14** · `docs/metrics-spec.md:30`: every refused submission writes a `spam_submission_blocked` row with no cap, so a bot flood grows the 500 MB Free database without limit. Fix: record at most one refusal event per address hash per reason per minute (count the rest in the next row's `properties.count`), or sample. Owner: architect.
- **SEC-15** · `docs/SECURITY_MODEL.md:69` (invariant 13): there is no `script-src` CSP, although session cookies are readable by JavaScript by design (`openapi.yaml:505`), so any XSS becomes a 7-day takeover. Fix: add `default-src 'self'; script-src 'self' 'nonce-<per-request>'; connect-src 'self' <supabase-url>; img-src 'self' <supabase-url> blob: data:; object-src 'none'; base-uri 'none'` to invariant 13. Owner: architect.
- **SEC-16** · `docs/SECURITY_MODEL.md:63` (invariant 7): the first-bytes check does not limit pixel dimensions (a 5 MB PNG can decode to gigabytes and crash the staff browser), and photos keep EXIF GPS. Fix: refuse PNG and WebP whose header dimensions exceed 12,000 px per side (the IHDR and VP8 headers sit in the first bytes already read), show photos with a plain `<img>` (no `next/image` remote optimisation of signed URLs), and record EXIF as accepted for staff-only viewing. Owner: architect, frontend.
- **SEC-17** · all `revoke insert, update, delete, truncate, references, trigger … from authenticated` lines (e.g. 0300:90): the migrations depend on Supabase's default grants for `select` and leave `MAINTAIN` (Postgres 17) in place. Fix: `revoke all on table … from authenticated; grant select on table … to authenticated;` for the six readable tables, so the result does not depend on project defaults. Owner: architect.
- **SEC-18** · `supabase/migrations/20261120000100_extensions_and_helpers.sql:10`: pgTAP, with its SQL-text-executing functions, is installed in every environment, including production. Fix: install pgTAP from the test runner only (or `revoke execute on all functions in schema extensions` for pgTAP's functions from `anon` and `authenticated` in production). Owner: architect.
- **SEC-19** · `docs/SECURITY_MODEL.md:49, 67, 73`: one `APP_SIGNING_SECRET` keys the form token and the IP and email hashes, and only the token input is domain-separated. Fix: specify the HMAC inputs as `ip|v1|<address>` and `email|v1|<lower-cased trimmed email>`, or derive one key per purpose with HKDF. Owner: architect.
- **SEC-20** · `docs/integration-contract.md:85` and `docs/architecture.md:227`: `GHL_API_BASE_URL` can point the token at any host. Fix: in production (`VERCEL_ENV=production`) the client accepts only `https://services.leadconnectorhq.com` and ignores the override. Owner: architect, integration.
