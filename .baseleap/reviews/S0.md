### The brief's items
1. **Consent field, the job trigger, the 409 retry refusal: confirmed.** All three are covered by the SEC-6 row. Both trigger functions are security invoker with `search_path = ''`, and execute is revoked from public (`0300:120-133`, `0400:56-68`). They run as whoever writes the row, and both writers bypass RLS: the service role, or `postgres` inside `change_quote_request_status`. A writer without BYPASSRLS would not see the request, so the trigger would refuse: it fails closed. **Gap:** the trigger fires on `insert` only, while `service_role` holds `update` on every column of `ghl_sync_jobs` (`0400:71, 79`): SEC-23 (Minor).
2. **One contact per homeowner (same email or phone).**
   - **Data across homeowners: none exposed through our app.** The copy runs after the HTTP response (`after()`, `docs/integration-contract.md:64`), so no response depends on whether a match exists, and there is no enumeration oracle. `find_ghl_contact_match` and `ghl_stage_for_request` are service-role only (`0600:814-815, 841-842`; `all_tables.sql:66-73`). They consider consented requests only, on both sides (`0600:808, 810, 835, 839`). Linking sends tags only, never contact fields (`integration-contract.md:26, 38, 46`), so a stranger's details never overwrite a homeowner's contact. Nothing read from GHL is shown on a request, apart from the copy state.
   - **Linking to someone else's contact: yes.** Anyone who types a homeowner's phone or email links to her contact, and by "last change wins" (`0600:837`) the newer request sets her stage tag. Pre-creating a contact for her email with your own name and phone also works, because fields are never updated. Both are integrity issues on a third party's GHL record, not data exposure: SEC-22 (Minor).
3. **`take_sign_in_attempt()`: confirmed.** The numbers and the restart are in the SEC-11 row.
   - **No deadlock:** every call takes the email lock before the address lock, and the two key spaces use different prefixes (`sign_in_email:`, `sign_in_ip:`).
   - **Fail closed:** the function swallows no error, and null keys raise PT422 (`0600:322-324`). The route answers any error with 503 without calling Auth (`SECURITY_MODEL.md:51`).
   - **No Retry-After:** `retry_after_seconds` stays on the server (`0600:308-309`), and the 429 body is the same for both limits and for unknown emails.
   - **Limit of the tests:** pgTAP runs on one connection, so the "parallel" tests are sequential calls in one transaction. QA's parallel probe is still the proof.
4. **`record_spam_refusal()`: confirmed** (SEC-14 row). The cap is exact under concurrency. The per-key lock serialises one address and reason, and the global lock serialises the daily count and the insert of a new event. The address key never reaches `events` (tested `submission_and_limits.sql:112-115`). The column-level `update (properties)` grant lets the server change only that column, and the key allow-list still applies on update (tested `rls/spam_refusal_windows.sql:47`).
5. **`rejected` (GHL 400, 404, 422): confirmed.**
   - The check constraint allows the class (`0400:23`).
   - `finish_ghl_job` turns `retry` with `auth`, `config_missing` or `rejected` into `failed` (`0600:681-683`). It accepts the class (`:747-750`) and records no `gave_up` for it (`:767`).
   - A 400 on create triggers one more duplicate search and never parses the 400 body for an id (`integration-contract.md:84`). That avoids trusting provider text. The SEC-12 charset check still applies to any id.
   - Tests: `complete_and_sync.sql:187-198`.
   - A provider error body must never be logged (invariant 11). That is unchanged.
6. **Tab routes and `next`: confirmed, no open redirect in the contract.**
   - `^/(requests|pipeline)(/[0-9a-f-]{36})?$` (`SECURITY_MODEL.md:93`) admits only same-origin absolute paths.
   - `//host`, `/\host`, `https:`, `javascript:`, `..`, any `%` and query strings all fail the character class.
   - JavaScript's `$` without the `m` flag does not match before a trailing newline. `URLSearchParams` has already decoded `%2F` and `%0A`, and the decoded forms fail the pattern too.
   - Both detail paths use `getQuoteRequest`, which is RLS-scoped (404 for pending).
   - **Phase 4:** the pattern must be used exactly as written, server-side or client-side, with no extra decode after the test. Add `next=/\evil.example` and `next=/requests%0A` to the build test list (`architecture.md:283`).
7. **The test asserting no password-reset path: confirmed for what it asserts, not sufficient on its own.**
   - `all_tables.sql:75-79` proves that no function in `public` has `password`, `reset` or `recover` in its name. That is the database half of invariant 21.
   - It says nothing about app routes, pages, links, or calls to `supabase.auth.resetPasswordForEmail` or `updateUser({ password })`, which is where a reset path would actually appear. It also uses case-sensitive `~` (harmless for unquoted names).
   - The app half is a Phase 4 check (rule proposal below) and a QA probe (AC-004.10). This is not a finding: invariant 21 states the app half, and it cannot be checked before code exists.
