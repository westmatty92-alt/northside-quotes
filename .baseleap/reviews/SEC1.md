### Why it is Minor now, not still Important
In round 2 the open path was a **future** malicious release of any of ~54 floating packages, picked up silently at the next venv rebuild. That path is now closed. A rebuild installs these 53 wheels byte for byte. A new upstream release, a re-uploaded file or a tampered mirror fails the hash check, and `run.sh` exits 3 `NOT RUN`. What is left needs one of 53 exact, widely used wheels (hypothesis, httpx, requests, jsonschema, pytest and so on) to have been malicious **already** when Matthew locked it on 2026-11-26. That is a fixed, known set, and it can be checked after the fact against advisories for those exact versions. Under sec-supply-chain §1 this is dev tooling, now with a closed and auditable dependency set. The residual impact below is real, but the likelihood is low, which makes it Minor.

### Residuals (stated plainly; open as Minor, not closed)
1. **The child's working directory is still the repo root, and `HOME` is passed through.** `run.mjs:73` runs `process.chdir(ROOT)`, `spawn` at `run.mjs:255` sets no `cwd`, and `child-env.mjs:14` lets `HOME` through. Neither is changed since round 2, and QA did not apply the interim reduction. So a locked package that was compromised at lock time could still `open('.env.local')` and read `BASELEAP_LEDGER_SERVICE_KEY` (Baseleap Console, spans clients), `SUPABASE_STAGING_DB_URL`, both service-role keys and the QA passwords. It could also read `~/.ssh`, git and `gh` credentials. **The impact is unchanged. Only the likelihood dropped.** Fix direction (QA, `tests/fuzz/run.mjs`): spawn with `cwd` and `HOME` set to a fresh `fs.mkdtempSync` directory, and pass `docs/openapi.yaml`, `--config-file` and `--report-dir` as absolute paths. Separately, move the ledger key out of `.env.local` (see Pre-existing).
2. **The bypass header and the staff token are still in `argv`, and in clear text in the HAR files.** `run.mjs:204` (bypass) and `:216` (owner's staging access token) are `--header` arguments, so other users on the same host can read them through `/proc/<pid>/cmdline` while a run is going. `run.mjs:252` writes `--report junit,har`. By the HAR format, the request headers sit in `.baseleap/tools/fuzz-reports/{anonymous,staff,jobs}/har-*.json`, which `.gitignore:3` ignores. Nothing deletes or redacts them after `serverErrors()` reads them (`run.mjs:222-245`). I did not open the HAR files, to avoid reading a secret. The token expires with the Supabase session. The bypass value lasts until it is rotated. Fix direction: delete or header-redact the HAR files once `serverErrors()` has read them, and pass both headers through a `0600` temp config file instead of `argv`.
3. **The unhashed fallback is still reachable.** `run.sh:62-66`: if the lock is missing (deleted or renamed) and the venv is missing or holds another version, `run.sh` installs floating, unhashed `schemathesis==4.0.0` with sdists allowed, and only warns (`:76`). Nothing makes the lock mandatory. Fix direction: a missing lock calls `not_run` (exit 3) instead of falling back.
4. **The comments now say the wrong thing.** `run.sh:30-34` says the lock "does NOT exist yet" and that floating dependencies are acceptable because the child gets no secret. `child-env.mjs:3` says the packages "are not hash-locked". All of that is now false, and the "no secret" premise was already wrong in round 2 (residual 1). Fix direction: say the lock is mandatory and the residual risk was accepted at Gate 3.
5. **The hashes are trust-on-first-use.** They record what PyPI served on 2026-11-26. They show the files haven't changed since, not that the files were safe. Some pins were days old when locked (`certifi==2026.11.20`). I could not run OSV on the lock (scanner not installed, `security-scan.sh` refused). The input file (`/tmp/fuzz-req.in`, lock line 2) isn't committed, so a regeneration relies on the comment at `run.sh:35-37`. Suggestions: add `tests/fuzz/requirements.lock` to the OSV step of `scripts/security-scan.sh` (my file; a proposal for the next security step, not done here because this round is read-only). When regenerating, add a release cooldown (`uv pip compile --exclude-newer <a date about 7 days back>`).
6. `pip` itself (24.0) is not in the lock. It comes from the interpreter's bundled `ensurepip` wheel, not from the network. Negligible.

**Residual risk in one line, for Gate 3.** Future upstream compromises can no longer reach the fuzz. If one of the 53 wheels was already malicious when it was locked on 2026-11-26, it could still read `.env.local` from its working directory (including the cross-client ledger key), plus the bypass value and staff token from `argv` and the HAR files. Residuals 1 and 2 close that path.

**Signature:** the original (`supply-chain: fuzz venv installs unhashed transitive deps and inherits full .env.local`) is resolved for the install. The residual is tracked as `supply-chain: fuzz child runs in repo root with .env.local readable`.

**Why it is not closed or downgraded: the premise of the fix doesn't hold.** `run.sh:32-34` accepts the floating dependencies "only for as long as the fuzz never gets a secret … run.mjs gives Schemathesis an allow-list environment, so it does not". The code shows otherwise:
- **`.env.local` is in Schemathesis's working directory.** `run.mjs:73` runs `process.chdir(ROOT)`, and `spawn` at `run.mjs:255` sets no `cwd`, so the child starts in the repo root, where `run.mjs:93` itself reads `.env.local`. The child runs as the same user, so any imported package can `open('.env.local')`. Reading `.env` files from the working directory is standard behaviour for PyPI credential stealers, not an exotic one. The same holds for the fallback `pip install` (`run.sh:12`, `:63`), where sdist build code runs in the repo root. `HOME` is passed through as well, so `~/.ssh`, git and `gh` credentials are reachable.
- **Two secrets reach the child by design.** The bypass value and the owner's staging token arrive in its own `argv` (`sys.argv`), and the HAR files store them on disk.
- **The worst-case impact has not changed.** By `.env.example`, that file still holds `BASELEAP_LEDGER_SERVICE_KEY` (the Baseleap Console, which spans clients), `SUPABASE_STAGING_DB_URL`, both service-role keys and the QA passwords.

**What did change: likelihood, not impact.** Malware that only dumps `os.environ` now gets nothing, and the pip build step no longer inherits the shell's credentials. The exposure window is the same as in round 1: a bad transitive release has to be picked up at a venv rebuild (a fresh machine, a deleted venv or a version bump). From then on it runs on every fuzz run. That narrows the realistic attack, but it does not reach the bar for Minor. sec-supply-chain §1 allows Minor for dev tooling only when it doesn't run with secrets, and this tooling runs with a cross-client key readable from its working directory. The tooling never ships to production. That limits who could be hurt (Baseleap and staging, not Northside's homeowners), but it does not limit how badly.

**Residual risk in one line, for Gate 3.** If any one of 54 unpinned PyPI packages is compromised before the next venv rebuild, that release can read `.env.local` from its working directory and send out the Baseleap ledger key, the staging database URL and the service-role keys. Exploitation needs an upstream compromise; damage if it happens is high and reaches beyond this client.

**What would change the rating**
- **Lock committed and used → Minor.** No code change is needed beyond the lock itself, because `run.sh:57-61` already installs it with `--require-hashes --only-binary=:all: --no-deps`. What remains after that is the `argv` and HAR copy of a staging bypass value and a short-lived staging token, handed only to a hash-pinned, known set of packages: Minor. It needs **one command by someone with pip/uv and network approval** (QA's session refuses both), from the comment at `run.sh:35-37`: `uv pip compile --generate-hashes --python-version 3.12 <input with "schemathesis==4.0.0"> -o tests/fuzz/requirements.lock`, then commit the file. Then one `bash tests/fuzz/run.sh` should print "Install source: … hash-locked" (`run.sh:74`).
- **Interim reduction (QA can do it now, no network; reduces the risk but does not downgrade it alone).** Spawn Schemathesis with `cwd` and `HOME` set to a fresh `fs.mkdtempSync` directory, passing `docs/openapi.yaml`, `--config-file` and `--report-dir` as absolute paths (`run.mjs:252,255`). Run the fallback `pip install` from that directory with `HOME` set to it (`run.sh:56,63`). That defeats working-directory and home-directory harvesting, but not a package that walks the filesystem. Also correct the comment at `run.sh:32-34`: the risk is accepted at a gate, not made safe by the environment.
- **Or Matthew rules it acceptable at Gate 3** (`stack-gatekeep` §4), with the lock as a tracked follow-up. Downgrading to Minor with the lock as a follow-up amounts to that ruling, so it is Matthew's call at the gate, not mine. My recommendation is to generate the lock before Gate 3: it is the cheapest of the three options.

### Brief item: the auth proxy (`src/proxy.ts`, `src/lib/server/auth/known-paths.ts`)
- **Not a security boundary, and it doesn't claim to be** (`proxy.ts:16-17`). Each `/api` handler authorises itself (route map). The staff pages hold no data: they fetch it through bearer-authenticated `/api` calls. A path that slipped past the proxy would at worst reach the platform's own not-found handling (the BUG-QA2-1 symptom: a 200 with the app shell). It could not reach data or skip a route's own check.
- **Shadowing a real route:** a route or page missing from the hand-kept list would 404 in production (an availability bug, failing closed). `tests/unit/proxy/known-paths.test.ts:37-52` compares both lists with `src/app` **in both directions**. It also forbids catch-all routes, metadata routes and parallel-route defaults, which the list would not see. Patterns become `[^/]+` per parameter; no route name contains a regex metacharacter, so a pattern can't match more than intended. Trailing slashes are stripped before matching (`proxy.ts:32`), and matching is case-sensitive like Next's router (`/API/…` and `/Requests` go to the 404).
- **Bypass:** the matcher skips only `_next/static`, `_next/image` and `favicon.ico` (`proxy.ts:107`). A path that uses this (for example `/_next/staticX`) gets no proxy, so it gets no CSP and no 404 from us. It reaches no app route or data. Next 16.4.6 is past the `x-middleware-subrequest` bypass. Encoded segments (`%2F`, `..%2F`) stay inside one `[^/]+` parameter and fail each route's UUID check (404).
- **Residual (no finding):** the 404 page and the 404 problem come from the proxy. Whether `next.config.ts` `headers()` adds `X-Frame-Options` to proxy-generated responses is unverified. It doesn't matter: the 404 page has no script and carries `frame-ancestors 'none'` in its own CSP (`proxy.ts:79`).

### Brief item: sign-in CSRF (non-JSON → 400)
- `requireJsonContentType` runs first in the handler, before the body is read or anything is counted (`sign-in/route.ts:15`; `http.ts:262-265`). Only `application/json` (any case, with parameters) passes; anything else is 400 `bad_request` with no 401 and no counter row.
- **Why that closes CSRF here:** a cross-site page can send only CORS-safelisted bodies (`text/plain`, `application/x-www-form-urlencoded`, `multipart/form-data`) without a preflight. `application/json` forces a preflight, and the app sends no `Access-Control-*` header anywhere, so the browser never sends the request. Before this change, a `text/plain` form post carrying JSON text could burn the victim's network-address quota or the owner's email quota, and in theory sign a victim into an account the attacker controls. Both are now impossible from a browser. `sendBeacon` with a JSON Blob is refused by browsers as a non-safelisted type.
- **Rating:** effective and correctly placed. **No residual cross-site path.** The staff API is bearer-only (no ambient credential); the two public routes require the custom `X-Form-Token` header, which is checked before anything is counted (`submissions.ts:204`; the time-trap refusal is recorded only for a validly signed token). An `Origin` check would be optional defence in depth, not needed for this threat. QA2 PRB-08 is the regression test.
