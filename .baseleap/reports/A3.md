### Checks behind the wording
- **Cursor format (CA-2).** `origin/staging:src/lib/server/services/quote-requests.ts`: `encodeCursor` returns `'c1.' + Buffer.from(JSON.stringify([submittedAt, id])).toString('base64url')`. Node's base64url has no `=` padding, so the issued alphabet after the prefix is exactly `[A-Za-z0-9_-]`. `decodeCursor` already refuses anything over 200 characters, without the `c1.` prefix, or failing `^[A-Za-z0-9_-]+$` after it with 400 `bad_request`, and then checks that it decodes to a calendar-valid UTC time and a lower-case uuid. The pattern matches what the server writes and refuses.
- **int32 (CA-1).** `quote_requests.version integer not null default 1 check (version >= 1)` (migration `20261120000300`); `save_quote_request_quote` and `change_quote_request_status` take `p_expected_version integer`; `list_quote_requests` returns `version integer` (`20261120000600`). The backend's `Version = z.int().min(1).max(2_147_483_647)` matches.
- **signIn Content-Type.** `origin/staging:src/app/api/auth/sign-in/route.ts` calls `requireJsonContentType(req)` first ("before anything is read or counted"). `http.ts` throws `ProblemError(400, 'bad_request')` unless the media type, lower-cased and without parameters, is `application/json`, and that includes a missing header. I did not claim "not counted" for a body that is `application/json` but not parseable, because I haven't read how `src/lib/server/auth/sign-in.ts` treats `UNPARSEABLE`.
